# Deploying the demo on Render (Docker, mock backend only)

> **Prototype. Not for real patient data.** This is a throw-away demo. The mock backend writes placeholder text, not
> medical content, and the child explanation is always replaced by the safe message in this mode (the mock writes 9
> sentences and the gate allows 8). Do not enter real patient information.

## What is deployed

* One Docker web service built from `deploy/Dockerfile` (repository root is the build context).
* `APP_BACKEND=mock`: no model file, no torch, no llama-cpp-python. Python packages: `requirements-app.txt` plus the five
  pins in `deploy/requirements-deploy.txt` (all copied from `requirements.txt`).
* Start command (inside the image): `python -m uvicorn app.web.main:create_app --factory --host 0.0.0.0 --port ${PORT:-10000} --workers 1 --no-server-header`.
  It has to be **one worker**: the job queue and the login throttle live in that process's memory.
* Runs as a non-root user (uid 10001). The SQLite file is `/data/familycare.sqlite3` (`APP_DB_PATH`).
* Health check path: `/` (the public welcome page, HTTP 200 without logging in). The app has no dedicated `/health` route.
  Render's documentation says health checks are "HTTP GET requests", that any 2xx or 3xx counts as healthy, and that
  the instance must answer within five seconds. (`HEAD /` returns 405 in this app; Render's docs do not mention HEAD.)

## Steps

1. Push this repository to GitHub (it is already at `advika75/family-care-circle`).
2. In Render: **New > Blueprint**, choose the repository and the branch.
3. In the Blueprint form, type **`deploy/render.yaml`** in the **Blueprint Path** field. (Render's docs: "If needed,
   specify a custom file path to your Blueprint's YAML file in the **Blueprint Path** field"; by default it uses
   `render.yaml` at the repository root.)
   Manual alternative: **New > Web Service**, runtime **Docker**, Dockerfile path `./deploy/Dockerfile`, Docker
   context `.`, instance count 1, health check path `/`, and add the variables listed below.
4. Create it. `APP_SECRET_KEY` is generated by Render (`generateValue: true`); nothing secret is stored in the repository.
5. When the deploy is live, open the service URL: you should see the welcome page. Check the footer reads
   "Prototype. Not for real patient data."

### Environment variables you set

| Variable | Value on Render | Note |
|---|---|---|
| `APP_BACKEND` | `mock` | the image cannot run `llama_cpp` |
| `APP_HTTPS` | `1` | Render terminates TLS; this makes the session cookie `Secure` and sends HSTS |
| `APP_SECRET_KEY` | generated | CSRF key; a stable value keeps open sign-in forms valid across restarts |
| `APP_DB_PATH` | `/data/familycare.sqlite3` | must be a writable directory |
| `APP_JOB_ISOLATION` | `thread` | correct for the mock backend |
| `APP_TRUSTED_PROXIES` | *unset at first* | see next section |

`PORT` is set by Render (default `10000`); the start command reads it. All variables are listed with placeholders in
`deploy/.env.example`.

## `APP_TRUSTED_PROXIES` on Render

**What the code does (verified by reading and by tests):** the app takes the client address from the socket peer.
`X-Forwarded-For` is believed **only** when the peer's address is listed, exactly, in `APP_TRUSTED_PROXIES` (no ranges). uvicorn's own
proxy handling is on by default but trusts only `127.0.0.1` (its default), so on Render the app sees Render's proxy address,
not the visitor's. I checked uvicorn 0.54's code: setting `--forwarded-allow-ips '*'` would make it take the
**left-most** `X-Forwarded-For` entry, which a visitor can forge, so this deployment does **not** do that.

**What that means with the variable empty (the state of the first deploy):** every visitor looks like one address, so
**all visitors share one throttle bucket: 10 sign-up attempts and 60 logins per 15 minutes in total**. A busy public
demo (or one person mistyping) can therefore **lock new visitors out for up to 15 minutes**. Wrong-password limits are also
counted per account plus that shared address. If someone sees "too many attempts", wait 15 minutes, or restart the service
(the throttle is in memory and resets on restart).

**How to fix it from Render's logs:** open the service's **Logs**, load a few pages, and read the address at the start of
each uvicorn access line (`INFO:  <address>:<port> - "GET / HTTP/1.1" 200 OK`). If every line shows the same address (or a
short stable list), set `APP_TRUSTED_PROXIES` to those exact addresses, comma-separated, and redeploy. If the addresses vary
without a pattern, leave it empty. Afterwards check from two different networks that a failed login on one does not block the other.

**What I could not verify:** Render's documentation (pages I fetched: *Web services*, *Blueprint spec*) does not state
which headers Render sets for the client address or whether its proxy addresses are fixed. I could not test against a real
Render service. To set the variable safely: deploy, open the service **Logs** and look at the address in the uvicorn
access lines (`INFO: <address>:<port> - "GET / ..."`); if every request shows the same address (or a short stable list),
set `APP_TRUSTED_PROXIES` to those exact addresses and redeploy. If the addresses vary between requests, leave it empty.
Only then check that two different visitors are no longer counted together.

## Demo accounts, safely

* **Recommended:** sign up through the site. Use obviously fake names and `@example.test` addresses and a throw-away
  password you do not use anywhere else. Create a profile, invite a caregiver, patient and child with the invitation
  codes, then paste a synthetic note (see `data/raw/` for examples).
* `python -m app.dev_seed` creates four demo accounts and two synthetic notes, but only in an **empty** database
  (it refuses otherwise) and it prints the passwords once to the terminal. It needs a shell in the running service
  (Render Shell). *Not verified: whether Render Shell is available on the free plan.* Run it as
  `APP_SEED_PASSWORD='<12+ characters you choose>' python -m app.dev_seed` so the password never appears in a file.
* Never put a real password, key or token in `render.yaml`, the Dockerfile or any file in this repository.

## What happens to data

* **Free plan (as shipped):** the filesystem is ephemeral. Restarting, redeploying or the instance spinning down
  after inactivity starts a **new, empty database**: accounts, profiles and notes are gone. I confirmed locally that data
  survives `docker restart` of the same container but not a new container.
  Whether and when Render's free plan spins an idle service down is a Render policy I did not verify.
* **Persistent disk (optional, paid):** in `render.yaml` change `plan` to a paid plan and uncomment the `disk:` block
  (mounted at `/data`). Render: persistent disks exist only on paid plans, and "any changes you make to a service's local files are
  lost every time the service redeploys or restarts" without one. A service with a disk cannot be scaled, which is what we want anyway.
  Back up the SQLite file yourself; there is no backup feature in the app.

## Keeping accounts on Render (why logins stop working, and two ways to fix it)

**Cause.** The app keeps every account, session, profile and note in one SQLite file (`APP_DB_PATH`, `/data/familycare.sqlite3` in this image).
On Render's free plan that file sits on an ephemeral filesystem, which Render says is "lost every time the service redeploys
or restarts". After a restart the app starts with a new, empty database, so the account you created no longer exists and
logging in returns "wrong email or password". Locally the same file lives on your disk and survives restarts: I created an
account, stopped the server, started it again and logged in successfully (HTTP 303). The local default is
`app/var/familycare.sqlite3`; the local demo (`make app-demo`) uses `app/var/demo.sqlite3`.

**Option 1: a paid persistent disk (small change, recommended).** The block is already in `deploy/render.yaml`, commented out:

```yaml
    # OPTIONAL persistent disk (paid plans only; Render: "a paid Render web service"). To use it: change `plan` above to
    # a paid plan id from Render's plan list (for example `0.5c-512mb`), then uncomment this block.
    # disk:
    #   name: fcc-data
    #   mountPath: /data
    #   sizeGB: 1
```

To enable it: (1) in `render.yaml` change `plan: free` to a paid plan id (`0.5c-512mb` is listed in Render's blueprint spec; check the
current price list); (2) delete the leading `# ` from the four `disk:` lines (keep the indentation, so `disk:` lines up with
`plan:`); (3) commit and redeploy (or **Manual Deploy**). The disk is mounted at `/data`, which is where `APP_DB_PATH` already points,
so no code change is needed. Render says a service with a disk cannot be scaled (we run one instance anyway) and `sizeGB` can be
increased but not decreased. Back up the SQLite file yourself; the app has no backup feature.

**Option 2: move the data to Postgres (a real code change; not started).** Based on reading `app/`:

* What would change: `app/db.py` (connection, transaction and migration runner), `app/migrations.py` (SQL types and
  `COLLATE NOCASE`), and every SQL call in `accounts.py`, `circle.py`, `notes.py`, `outputs.py`, `permissions.py` and `jobs.py`
  (about 70 `execute` calls in 8 files, around 1,400 lines of data-layer code). Specific points: `?` placeholders become `%s`;
  `cursor.lastrowid` (10 uses) becomes `INSERT ... RETURNING id`; `sqlite3.Row` and `sqlite3.IntegrityError` (13 imports, 3 catches) need the
  new driver's equivalents; `BEGIN IMMEDIATE` (used so that a single-use invitation code cannot be redeemed twice at once) needs an
  explicit lock or a serializable transaction, although the conditional `UPDATE ... WHERE used_at IS NULL` that enforces it is portable;
  case-insensitive unique email needs `citext` or a `lower(email)` index; the PRAGMAs and WAL setup go away.
* What would not change: the web layer, templates, permissions logic, safety gate, in-memory job queue and throttle.
* New things needed: a Postgres driver (a **new Python dependency**, which this project's rules do not allow without your approval),
  a Render Postgres instance and its connection string as a secret environment variable. Render's free Postgres tier terms (for
  example whether the database expires) were not checked.
* Size: roughly **2 to 4 days** for one developer, most of it in the tests. The 596 app tests build throw-away SQLite files, so they
  would need either a Postgres test database or a thin switch that keeps SQLite for tests, and the concurrency tests (invitation
  race, queue claim) must be re-proved on Postgres. This estimate is from reading the code, not from trying it.
* Recommendation: for a demo, Option 1, or simply re-create the demo accounts after a restart (`make app-demo-seed` locally; sign up
  again on Render). Do Option 2 only if the app is going to be kept online for real users.

## Known limits of this deployment

* No real model: every note produces placeholder text from the mock backend. Every output card shown to the creator,
  caregiver, patient and child carries the line "Placeholder output from the mock backend. Not generated by the language
  model." (shown only when `APP_BACKEND=mock`; covered by `tests/app/test_app_mock_label.py`).
* Single instance, in-memory job queue and throttle, no email, no password reset (see `app/README.md`, "What is NOT secured").
* `httpx` (a test-only dependency) is installed because it is in `requirements-app.txt`; `pip-audit` flagged an advisory in
  its dependency `certifi`, which the app never uses at runtime (no outbound calls).
